## Amendments

### A1. Catalog commands join the sync protocol

`SyncCommand` is now `issueInvoice | catalogWrite`. The catalog command is an ordered list of row writes defined in `packages/contracts/src/catalog/write.ts`. Every write is executed inside the same organization-locked transaction as invoices and recorded in the same change log, so replicas receive catalog changes through the ordinary pull.

Conflict rules, refining section 6 of the authority plan:

- An upsert with `expectedRowVersion: null` is an insert; an existing id under another operation is `ENTITY_CONFLICT`.
- Category fields are last-writer-wins. Deleting a category requires a matching row version and no active products.
- Product fields are last-writer-wins, except `unitsPerPack`: changing it requires a matching row version and passes the remaining-stock rule. `categoryId` must reference an active category.
- Batch upserts always require a matching row version because they carry absolute stock counts. Quantity changes create a `stock_in` movement on insert or an `adjustment` movement on update, with the client-chosen `movementId`.
- Deletes are soft deletes with a bumped row version and are published as `delete` log changes carrying the row image.
- A category name already used by another category in the organization is rejected with `ENTITY_CONFLICT`.
- Every failure raised by a command body after identity, sequence, epoch, and ownership checks pass is recorded as a rejected receipt that consumes the replica sequence. Only `ORGANIZATION_MISMATCH`, `INVALID_PAYLOAD_HASH`, `OPERATION_ID_REUSED`, `REPLICA_SEQUENCE_GAP`, `EPOCH_MISMATCH`, `REPLICA_UNKNOWN`, and `REPLICA_OWNED_BY_OTHER` fail the request. Clients never abandon commands locally; a rejected receipt is the only terminal path.
- Imports are lowered on the client into product and batch upserts and chunked at 500 lines per command so no command exceeds `MAX_CATALOG_WRITE_ROWS`; each chunk is atomic on its own.

### A2. Pending projections are visible locally

Section 8 of the authority plan requires an optimistic projection in the enqueue transaction. The implementation writes provisional rows ("shadow rows") into the entity stores marked with the pending operation id, keeps a per-command journal of prior images, and applies these rules:

- Integration of the same operation replaces shadows with authoritative rows and clears the journal.
- An authoritative image for a shadowed row from a different operation wins and clears that row's mark.
- Rejection restores prior images and deletes rows that had none.
- Snapshot activation re-applies shadows for outstanding commands in client-sequence order.
- Stock overlays stay relative; batch upserts carry absolute quantities in their shadow row and create no overlay.

### A3. Pull digest on request and byte budget

Computing a partition digest on every pull is too expensive for the largest tenant. The client sets `includeDigest` when it believes it is caught up; the server computes the digest in the same repeatable-read snapshot as the returned page and only when that page reaches the horizon. The digest function lives in `packages/contracts/src/sync/digest.ts` and is shared verbatim by both sides. Pull responses are additionally bounded by an encoded-byte budget derived from `MAX_TRANSPORT_PAYLOAD_BYTES`, never splitting a transaction group and always returning at least one.

### A4. Retention and snapshot stepping run on a scheduled Worker

Section 10 stays as written. The concrete shape: a Cloudflare Cron trigger on the API Worker (declared through Alchemy) invokes a bounded step that advances retention floors above active download leases and the newest published snapshot, deletes history in bounded batches, and continues staged snapshot jobs. Until this lands, the change log grows without bound and pulls after long offline periods get slower.

### A5. Browser entrypoint must be provably native-free

`packages/sync/src/browser.ts` must not transitively import `better-sqlite3` or Drizzle SQLite. Move the SQLite convenience constructor out of `engine.ts` into the `./sqlite` entrypoint and add an import-graph test so the boundary cannot regress.

### A6. Dead SQLite authority is removed

`packages/sync/src/authority/*`, `packages/db/src/inventory/*`, the `drizzle.inventory.config.ts` check, and their tests are deleted once the digest module has moved to contracts. They duplicate the Postgres rules and would drift.

### A7. Effect Atom and worker-hosted IndexedDB remain scheduled after functional parity

The frontend reactivity plan is unchanged but ordered after catalog commands, pending projections, retention, and the browser boundary. The renderer-thread IndexedDB path is acceptable for the current desktop web build and moves into a worker when the web target ships.

### A8. Electron replica moves to Effect's Node SQLite client

Electron 44 embeds Node 22.12 or newer, so `node:sqlite` is available in the replica worker. Replace `better-sqlite3` with `@effect/sql-sqlite-node` at the workspace pin through Drizzle's `effect-sqlite-node` driver, behind the unchanged `ReplicaStore` contract. This removes the native addon rebuild from packaging and gives the client the same Effect SQL client model as the server. Re-verify WAL, prepared statement reuse, the migration history, and interruption in the packaged app before deleting the old driver. Applied to `scripts/migrate-cloudflare` on 2026-09-22 (`src/sqlite.ts`, `src/target.ts`, `src/directory.ts`, `src/export-store.ts`). On 2026-09-27 the script's SQLite staging target dropped Drizzle for plain `@effect/sql-sqlite-node` statements and its PostgreSQL source moved from `pg` to `@effect/sql-pg`. Embedded Postgres stays in server tests because it is the database server under test, not a client.

### A9. Hard deletes everywhere the change log makes them safe

Decided 2026-09-22. Deletes already reach replicas as `delete` log changes carrying the row image, and snapshots never ship deleted rows, so replicas hard-delete on every `delete` action and drop `deletedAt` from client row schemas, local queries, the IndexedDB adapter, and the projections. On the server, `deleted_at` stays only on products and batches because invoice items and stock movements reference them; categories, invoices, and invoice items lose the column, category deletes become physical, and the category name uniqueness index becomes a plain unique index. Invoice history joins to products become left joins that fall back to the denormalized product name and batch number on the item row. Implementation notes from 2026-09-22: the replica schema drops all SQLite foreign keys because a sold-out batch the authority deletes is always referenced by movements and items, and the replica is a projection; on the server the product-to-category foreign key is dropped because soft-deleted products keep referencing their category, so `catalog-write.ts` validates the category on insert and change instead. The unused `inventory_mutation_receipts` table was removed in the same migration. Effect EventLog is not adopted; the change log is the audit trail, and telemetry export uses Effect's OTLP modules with Alchemy Logpush when needed.

### A10. Network and Postgres cost pass

Decided 2026-09-27. The protocol was correct but chatty: idle clients polled every two seconds, a command cost two requests and a wasted self-wake, every refresh read the session back, and the Worker rebuilt its router and verification key per request. The pass keeps every rule in sections 5 to 10 and removes requests and statements.

Clients:

- Cadence. An empty pull steps the scheduler down the ladder 5, 15, 30, 60, 300 s; an explicit wake (local write, focus, reconnect, live hint) resets it. While the live channel is connected the timer falls to one pull every five minutes. The live loop runs only while the window or app is visible and the replica owns the network (desktop blur and focus, mobile `AppState`).
- One cycle drains the outbox with one command in flight, then pulls page after page to the horizon (`packages/sync/src/engine.ts`). A live hint at or below the applied cursor is dropped, so a client's own commit no longer wakes a pull.
- Long-poll carries the bearer token and no ticket (`nonce` is optional on `/api/sync/live`); it waits 55 s by default and at most 85 s. SSE sends a keepalive every 25 s. Every transport call has a deadline (`SYNC_REQUEST_TIMEOUT_MILLIS`), and `Retry-After` on any status is honoured up to five minutes. A building snapshot retries after the server's hint; parts download four at a time and resume from staged parts.
- Push carries the pull page. `SyncSubmitCommandRequest` adds optional `afterCommitSequence` and `maxBytes` to the envelope, which already names the replica and epoch; `SyncSubmitCommandResult` adds an optional `page` in the `SyncPullResult` shape to the receipt. The engine settles the receipt and applies the page in one replica transaction (`settleUploadWithPage`; the IndexedDB adapter settles first and then applies the page with the same per-group transactions as a pull), and when the page reaches the horizon the cycle's follow-up pull is skipped unless digest verification is due. A page from another incarnation or any failure applying it falls back to settling the receipt alone and pulling as before. Absent fields mean today's behaviour in both directions.
- Pull byte budget. `SyncPullRequest.maxBytes` and the submit request's `maxBytes` are clamped by the server to `[MIN_PULL_BYTE_BUDGET, PULL_PAYLOAD_BUDGET_BYTES]` (64 KiB to 883,616 bytes). Mobile asks for 256 KiB on cellular and Bluetooth networks as reported by `expo-network` and omits it otherwise (`apps/mobile/src/inventory/policy.ts`); desktop leaves it unset. `SyncSchedulerPolicy.pullMaxBytes` sets a static default and `setPullMaxBytes` changes it at run time.
- Refresh carries the workspace. The refresh response adds an optional `workspace` in the `WorkspaceSnapshot` shape, built from the same values as the new token's claims (`sessionWorkspaceFromClaims` in `packages/auth/src/model.ts`). Desktop (`apps/desktop/electron/auth.ts`) and mobile (`apps/mobile/src/auth/controller.ts`) adopt it inside the refresh and drop the follow-up `GET /api/auth/session`, including the second read desktop made on boot and renew and mobile made after rename, join, and restore. An authority without the field is read as before.

Server and auth workers:

- The `HttpApi` router and the JWT verification key are built once per isolate, which also stopped SSE streams dying on a closed request-scoped pool. The live horizon is one statement shared per organization per isolate for one second.
- Receipt and pull are single statements outside a transaction; only a pull that asks for a digest opens the repeatable-read transaction. Pull headers are selected by the running sum of `inventory_transactions.byte_length`, persisted at commit and backfilled by migration, and change rows are read by range; stored JSON is spliced into responses without a decode and re-encode.
- A caught-up submit returns its own group from memory under the organization lock, so the page costs no statement; a client that is behind or retrying gets the same single-statement pull after the commit, outside the lock. The page is best effort and never fails a committed command.
- Snapshot acquire runs without the organization lock, reports stored entity counts, and never builds synchronously. Parts carry an `ETag` and `private, max-age=31536000, immutable`, and answer `If-None-Match` with 304.
- Locked writes are batched. Invoice issue is seven statements regardless of line count, catalog writes preload the touched rows by id, and change log inserts batch by a thousand rows.
- Refresh is two D1 round trips; an hourly cron (`23 * * * *`) prunes sessions a week past expiry. Building snapshots and rate limits answer with `Retry-After`.

Request counts after the pass, for a caught-up client: a command is one request (`POST /api/sync/commands`) instead of a command, a pull, and a self-wake pull, and Postgres runs the commit transaction and nothing else. A token refresh is one request instead of two; desktop boot or renew after an expired access token is one request instead of three, and so is mobile restore, rename, or join after a refresh.

Still open:

- Digest per-row leaf hashes, so verification can narrow a mismatch instead of forcing a snapshot.
- Actor and device fields move from every row image into the transaction header to cut row-image bytes.
- Desktop SSE through a streaming broker proxy; desktop long-polls today.
- The 600 s access-token TTL is an owner decision; a longer TTL removes refreshes, a shorter one narrows revocation.
- `EventSource` clients cannot send a bearer header, so SSE outside the proxies still needs a ticket or cookie scheme.

### A12. Operational snapshots carry invoice history

Decided 2026-09-28 by the owner. The operational subscription covers `category`, `product`, `batch`, `invoice`, `invoiceItem` and `stockMovement` with full history, so a freshly synced replica shows every invoice.

- Digest v3 (`PARTITION_DIGEST_VERSION = 3`, domain `store.sync.partition-digest.v3`) hashes all six entities with the v2 leaf format. Stock movements are append-only and have no `row_version`, so both sides use the constant leaf version 1 (`STOCK_MOVEMENT_ROW_VERSION`), matching the change log. `sync.partition_digest(org, version)` serves both versions; the one-argument form and `sync.pull` without a version stay on v2, so clients on 0.3.100 to 0.3.102 (which send `digestVersion: 2`) get the catalog-only digest byte for byte.
- Snapshots are always built with history (`snapshot_jobs.digest_version = 3`); catalog rows fill the leading parts and history starts on a fresh part (`catalog_parts`). Parts are bounded by 500 rows and a 512 KiB byte budget in the same statement. `AcquireSnapshotRequest.digestVersion` selects the view: without it the manifest lists only the catalog parts and the three catalog counts, exactly the shape old clients import (their import does not clear history tables and would hit the replica's invoice-number unique index on colliding shadow invoices). With `digestVersion: 3` the manifest lists every part and carries `digestVersion: 3`. Snapshots built before migration `20260928150000_history_snapshots` are never chosen for new acquisitions; the maintenance cron rebuilds them.
- Clients record the snapshot's digest version on the import, clear and bulk-insert exactly the covered entities on activation, carry local history only across catalog-only snapshots (IndexedDB), and renumber a pending shadow invoice whose number a snapshot invoice already holds.
- Backfill: replica migration `20260928150000_history_coverage` (and IndexedDB version 4) clears `verifiedAt`, so the first caught-up pull after the upgrade asks for a v3 digest. A replica without history diverges on the history entities, marks coverage for repair, and recovers through a v3 snapshot that keeps the outbox and re-applies pending shadows. The server migration must be deployed before clients that send `digestVersion: 3`, because older Workers reject the value.

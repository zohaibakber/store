## Amendments

### A1. Catalog commands join the sync protocol

`SyncCommand` is now `issueInvoice | catalogWrite`. The catalog command is an ordered list of row writes defined in `packages/contracts/src/catalog/write.ts`. Every write is executed inside the same organization-locked transaction as invoices and recorded in the same change log, so replicas receive catalog changes through the ordinary pull.

Conflict rules, refining section 6 of the authority plan:

- An upsert with `expectedRowVersion: null` is an insert; an existing id under another operation is `ENTITY_CONFLICT`.
- Category fields are last-writer-wins. Deleting a category requires a matching row version and no active products.
- Product fields are last-writer-wins, except `unitsPerPack`: changing it requires a matching row version and passes the remaining-stock rule. `categoryId` must reference an active category.
- Batch upserts always require a matching row version because they carry absolute stock counts. Quantity changes create a `stock_in` movement on insert or an `adjustment` movement on update, with the client-chosen `movementId`.
- Deletes are soft deletes with a bumped row version and are published as `delete` log changes carrying the row image.
- A category name already used by another category in the organization is rejected with `ENTITY_CONFLICT`.
- Every failure raised by a command body after identity, sequence, epoch, and ownership checks pass is recorded as a rejected receipt that consumes the replica sequence. Only `ORGANIZATION_MISMATCH`, `INVALID_PAYLOAD_HASH`, `OPERATION_ID_REUSED`, `REPLICA_SEQUENCE_GAP`, `EPOCH_MISMATCH`, `REPLICA_UNKNOWN`, and `REPLICA_OWNED_BY_OTHER` fail the request. Clients never abandon commands locally; a rejected receipt is the only terminal path.
- Imports are lowered on the client into product and batch upserts and chunked at 500 lines per command so no command exceeds `MAX_CATALOG_WRITE_ROWS`; each chunk is atomic on its own.

### A2. Pending projections are visible locally

Section 8 of the authority plan requires an optimistic projection in the enqueue transaction. The implementation writes provisional rows ("shadow rows") into the entity stores marked with the pending operation id, keeps a per-command journal of prior images, and applies these rules:

- Integration of the same operation replaces shadows with authoritative rows and clears the journal.
- An authoritative image for a shadowed row from a different operation wins and clears that row's mark.
- Rejection restores prior images and deletes rows that had none.
- Snapshot activation re-applies shadows for outstanding commands in client-sequence order.
- Stock overlays stay relative; batch upserts carry absolute quantities in their shadow row and create no overlay.

### A3. Pull digest on request and byte budget

Computing a partition digest on every pull is too expensive for the largest tenant. The client sets `includeDigest` when it believes it is caught up; the server computes the digest in the same repeatable-read snapshot as the returned page and only when that page reaches the horizon. The digest function lives in `packages/contracts/src/sync/digest.ts` and is shared verbatim by both sides. Pull responses are additionally bounded by an encoded-byte budget derived from `MAX_TRANSPORT_PAYLOAD_BYTES`, never splitting a transaction group and always returning at least one.

### A4. Retention and snapshot stepping run on a scheduled Worker

Section 10 stays as written. The concrete shape: a Cloudflare Cron trigger on the API Worker (declared through Alchemy) invokes a bounded step that advances retention floors above active download leases and the newest published snapshot, deletes history in bounded batches, and continues staged snapshot jobs. Until this lands, the change log grows without bound and pulls after long offline periods get slower.

### A5. Browser entrypoint must be provably native-free

`packages/sync/src/browser.ts` must not transitively import `better-sqlite3` or Drizzle SQLite. Move the SQLite convenience constructor out of `engine.ts` into the `./sqlite` entrypoint and add an import-graph test so the boundary cannot regress.

### A6. Dead SQLite authority is removed

`packages/sync/src/authority/*`, `packages/db/src/inventory/*`, the `drizzle.inventory.config.ts` check, and their tests are deleted once the digest module has moved to contracts. They duplicate the Postgres rules and would drift.

### A7. Effect Atom and worker-hosted IndexedDB remain scheduled after functional parity

The frontend reactivity plan is unchanged but ordered after catalog commands, pending projections, retention, and the browser boundary. The renderer-thread IndexedDB path is acceptable for the current desktop web build and moves into a worker when the web target ships.

### A8. Electron replica moves to Effect's Node SQLite client

Electron 44 embeds Node 22.12 or newer, so `node:sqlite` is available in the replica worker. Replace `better-sqlite3` with `@effect/sql-sqlite-node` at the workspace pin through Drizzle's `effect-sqlite-node` driver, behind the unchanged `ReplicaStore` contract. This removes the native addon rebuild from packaging and gives the client the same Effect SQL client model as the server. Re-verify WAL, prepared statement reuse, the migration history, and interruption in the packaged app before deleting the old driver. Applied to `scripts/migrate-cloudflare` on 2026-09-22 (`src/sqlite.ts`, `src/target.ts`, `src/directory.ts`, `src/export-store.ts`). Embedded Postgres stays in server tests because it is the database server under test, not a client.

### A9. Hard deletes everywhere the change log makes them safe

Decided 2026-09-22. Deletes already reach replicas as `delete` log changes carrying the row image, and snapshots never ship deleted rows, so replicas hard-delete on every `delete` action and drop `deletedAt` from client row schemas, local queries, the IndexedDB adapter, and the projections. On the server, `deleted_at` stays only on products and batches because invoice items and stock movements reference them; categories, invoices, and invoice items lose the column, category deletes become physical, and the category name uniqueness index becomes a plain unique index. Invoice history joins to products become left joins that fall back to the denormalized product name and batch number on the item row. Implementation notes from 2026-09-22: the replica schema drops all SQLite foreign keys because a sold-out batch the authority deletes is always referenced by movements and items, and the replica is a projection; on the server the product-to-category foreign key is dropped because soft-deleted products keep referencing their category, so `catalog-write.ts` validates the category on insert and change instead. The unused `inventory_mutation_receipts` table was removed in the same migration. Effect EventLog is not adopted; the change log is the audit trail, and telemetry export uses Effect's OTLP modules with Alchemy Logpush when needed.
